# 深度探究指南

本指南把 `expanded` 从“栏目更完整”提升为“能够解释因果并预测行为”。
知识总结的目标不是让读者记住更多名词，而是让读者在遇到相似输入、异常或设计选择时，能够说明：为什么会这样、哪一步决定了结果、证据支持到哪里、换一种条件会怎样。

深度不等于堆积更多测试、构建或工程过程。测试和运行结果只有在帮助解释
输入契约、边界、失败机制或证据范围时才进入正文；其余内容压缩为最小
验证边界或来源引用。

## 深度的判定标准

一条知识只有同时回答下面的问题，才算被探究，而不是被提及：

1. **现象与问题：** 观察到了什么，影响是什么，真正要解释或解决的是什么？
2. **机制与因果：** 输入经过哪些中间步骤、数据变换、状态变化或控制分支，为什么最终会得到这个结果？
3. **证据：** 哪个文件、符号、配置、命令、测试、日志或运行场景支持这条解释？证据的可信度和范围是什么？
4. **反事实：** 如果删掉、替换、延后或改变这个关键条件，结果会怎样？这是推理、已有测试，还是尚未验证的实验？
5. **失败与边界：** 哪些输入、环境、权限、时序或依赖会使机制不成立？失败时读者能观察到什么？
6. **迁移条件：** 这条规律何时可以复用，何时不能直接复用，识别信号是什么？

推荐用下面的链条组织关键知识，而不是用孤立的知识点列表：

```text
触发/输入
  → 前置条件与校验
  → 中间数据或状态
  → 关键机制/分支
  → 输出、副作用或可观察信号
  → 下一消费者
```

链条中每个箭头都要能回答“发生了什么”和“为什么在这里发生”。如果某个箭头没有源代码或验证证据，保留它的未知状态并写出最小验证办法。

## 六遍探究流程

### 第一遍：定义要解释的现象

不要从文件名或术语开始。先写清改动前的可观察行为、触发症状、影响、目标、非目标和约束。把“想要更好”改写成可以观察或验证的行为。

### 第二遍：追踪机制

选择一个真实输入或测试样例，沿入口、调用、转换、状态变化、输出和副作用跟读。对每个步骤记录输入来源、关键条件、中间结果、下一消费者和失败信号。不要只把调用链改写成文件列表。

### 第三遍：解释为什么这样设计

找出真正改变行为的约束或设计选择，比较至少一个相关替代方案。说明选择方案依赖的假设、获得的性质、接受的成本，以及哪些结论只是 `[推断]`。

### 第四遍：寻找反例和失败路径

至少选择一个相关异常、边界输入、缺失依赖、权限/配置差异或错误时序。说明它在哪一步偏离正常机制、如何表现、怎样用最小安全检查区分原因。没有执行过的反事实必须标为 `未验证`，不能写成事实。

### 第五遍：校准证据边界

把静态代码、单元测试、构建产物、集成测试和真实运行场景分开。每个重要结论写清“证据证明什么”和“不能证明什么”。测试未覆盖的路径不是“应该没问题”，而是验证缺口。

### 第六遍：提炼可迁移知识

从具体实现中抽象规则，但保留适用条件、不适用条件、反例和识别信号。不要把项目偶然的命名、目录结构或框架默认行为伪装成通用设计原则。

## 深度探究卡片契约

对每个核心概念、关键决策或重要故障，至少填写以下字段：

| 字段 | 必须回答的内容 |
|---|---|
| 要解释的问题 | 读者现在无法预测或判断的具体问题 |
| 结论 | 用一句话回答，但标注 `[事实]`、`[推断]`、`[计划]` 或 `[待确认]` |
| 通俗模型 | 不依赖术语的最小解释 |
| 机制 | 具体的中间步骤、数据/状态变化、条件和因果关系 |
| 证据 | 文件/符号/命令/测试/运行场景与可信度 |
| 反事实 | 改变关键条件后会怎样；若未执行则写 `未验证` 和验证办法 |
| 失败与边界 | 何时失效、可观察信号、不能推出的结论 |
| 迁移 | 适用条件、不适用条件和识别信号 |

“技术原理”不能只写名词定义；必须写出它如何改变当前项目中的数据、控制流或状态。“常见误区”不能只写提醒；要说明误区会导致什么错误预测。

## 各笔记的深度门槛

`expanded` 捕获不能因为模板字段已出现就算完成。写入预览前进行一次深度审计：

- `00-功能总览.md`：至少给出一个因果结论、一个主流程机制、一个关键假设或边界，并列出 3–7 个“为什么/如果改变会怎样”的关键问题；问题没有证据时明确列为待验证。
- `01-实现细节.md`：必须有一条带中间状态的正常路径和一条异常/边界路径；至少拆解一个“为什么这一步会改变行为”的机制，并给出一个反事实或替代方案。
- `02-实施效果.md`：必须把“证据 → 支持的结论 → 不支持的结论”逐项对应，至少指出一个未验证边界，不能把测试通过改写成整体可用。
- `03-知识应用总结.md`：至少两张知识卡；每张都要写原理、证据、适用与不适用条件、反例或失败信号和应用步骤。练习必须能检验机制理解，而不是只查找文件名。
- `04-后续迭代方向.md`：把深度缺口转成可执行事项，包含验证对象、方法和验收标准；没有缺口时写明“当前证据未发现需要新增探究的事项”。
- `99-相关对话与文件.md`：每个关键来源写“证明什么/不能证明什么”，让读者能复核因果解释，而不是只看到路径清单。

架构笔记还要解释边界和依赖方向为什么存在，并指出违反不变量时的表现；项目总览只做索引，不复制这些深层推导。

## 证据不足时怎么保持深度

证据不足不等于可以用泛化知识填空。应当：

1. 保留当前能确认的机制片段，并用 `[待确认]` 或 `未验证` 标出断点。
2. 写出断点需要的最小证据，例如一个具体测试输入、一段日志、一个调用者或一次运行场景。
3. 说明在证据补齐前，读者不能作出什么决定或保证什么行为。
4. 将验证动作放入后续迭代，并写明验收标准。

不要为了满足“至少一段解释”而编造调用链、内部实现、性能结论或未执行的反事实实验。

## 预览中的深度审计

默认预览增加一张“深度探究审计”表：

| 核心问题/知识 | 机制是否展开 | 证据位置 | 反事实/失败路径 | 边界 | 可迁移条件 | 状态 |
|---|---|---|---|---|---|---|

状态只能是“已展开”“部分展开（列出缺口）”或“无证据（列出最小验证）”。若只写了术语、文件名或结论，没有机制和证据边界，状态不能标为“已展开”。
